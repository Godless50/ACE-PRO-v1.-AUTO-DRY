# Автоматическая сушка ACE Pro по внешнему датчику влажности

Дата: 2026-09-26
Статус: дизайн утверждён, ожидает реализации

## Задача

Anycubic ACE Pro (rev. 1) под управлением multiACE на Snapmaker U1 должен
включать и выключать сушку филамента самостоятельно, по фактической влажности
внутри камеры. Сейчас сушка запускается только вручную кнопкой.

## Почему штатная автосушка не работает

multiACE содержит полностью готовый механизм автосушки: пороги, гистерезис,
мягкий разгон температуры ступенями, учёт идущей печати, сохранение состояния
между перезапусками, семантику владения циклом (цикл, запущенный руками, движок
не трогает). Механизм не запускается по одной причине — **у него нет источника
влажности**.

Влажность умеет сообщать только ACE 2. ACE Pro такого датчика не имеет, поэтому
в multiACE он может быть лишь «ведомым» (follower) при «мастере» ACE 2. При
единственном ACE Pro в системе мастера не существует, и движок простаивает.

Три места в `klippy/extras/ace.py`, где это проявляется:

| Строка | Код | Следствие |
|---|---|---|
| ~10885 | `if not self._is_v2(idx): continue` | цикл автосушки пропускает Pro до всяких проверок |
| ~10648 | `_ace_humidity()` читает только `_info_per_ace[idx]['humidity']` | у Pro это поле всегда пустое |
| ~8978 | `if not is_v2 and enabled and master < 0: cur['enabled'] = False` | галочка «автосушка» в UI гаснет сразу после включения |

Дополнительно, штатной командой `ACE_SET_AUTO_DRY` нельзя назначить Pro мастером
самому себе: `MASTER` проверяется на `_is_v2` и отклоняется.

## Решение

Внешний датчик влажности (Xiaomi LYWSD03MMC, BLE) измеряет воздух в камере ACE.
Сервер передаёт показания в Klipper. Все решения о нагреве принимает **штатный
механизм multiACE** — мы только снимаем запрет «только для ACE 2» и поставляем
число.

```
[Xiaomi LYWSD03MMC]  ──BLE──►  [ace-rh-feeder]  ──HTTP──►  [Moonraker]
   в камере ACE Pro            сервер <server-ip>          <printer-ip>:7125
                                                                 │
                                                        ACE_SET_RH ACE=0 RH=..
                                                                 ▼
                                                        [ace_ext_rh.py]
                                                     свой таймер, свои пороги нет —
                                                     берёт пороги из multiACE и
                                                     вызывает его же
                                                     _auto_dry_start / _auto_dry_stop
                                                                 ▼
                                                          [multiACE ace.py]
                                                       мягкий разгон, учёт печати,
                                                       сохранение состояния
                                                                 ▼
                                                            [ACE Pro]
```

### Ключевое решение: отдельный модуль, а не патч

`ace.py` не изменяется ни на строку. Причина: multiACE обновляется командой
`ACEH__UPDATE_APPLY`, которая перезаписывает файл целиком — патч исчезнет при
первом же обновлении, причём молча, и автосушка перестанет работать без
единого сообщения об ошибке.

Вместо этого создаётся отдельный модуль Klipper `ace_ext_rh.py`, который
обращается к объекту `ace` снаружи. Он переживает обновления multiACE.

Цена решения: модуль опирается на приватные методы (`_auto_dry_start`,
`_auto_dry_stop`, `_auto_dry_for`, `_auto_dry_cfg`). Обновление multiACE может
их переименовать. Поэтому модуль при старте **проверяет наличие каждого
используемого атрибута** и при отсутствии громко пишет ошибку в лог и
отключается, вместо того чтобы молча не работать.

### Обход сброса галочки

Валидация, гасящая `enabled`, живёт в обработчике G-code команды, а не в самом
движке. Модуль пишет конфигурацию напрямую в словарь и сохраняет её:

```python
ace._auto_dry_cfg['0'] = {'enabled': True, 'master': 0,
                          'rh_start': 45.0, 'rh_end': 35.0, 'temp': 50}
ace.save_variable('ace__auto_dry', ace._auto_dry_cfg, write=True)
```

`master: 0` — Pro назначается мастером самому себе. Это не косметика, а
необходимость: в конце каждого тика multiACE гасит «осиротевшие» циклы

```python
_m = int(self._auto_dry_for(f).get('master', -1))
if _m < 0 or _m not in self._auto_dry_started:
    self._auto_dry_stop(f, 'orphaned - master done before restart')
```

Без `master: 0` наш цикл был бы погашен в течение минуты после запуска.
С `master: 0` проверка проходит: индекс 0 присутствует в `_auto_dry_started`.

## Компонент 1: `ace_ext_rh.py` (принтер)

Размещение: `/home/lava/klipper/klippy/extras/ace_ext_rh.py`
Секция конфигурации: `[ace_ext_rh]` в `printer_data/config/printer.cfg`

### G-code команды

| Команда | Назначение |
|---|---|
| `ACE_SET_RH ACE=0 RH=42.5 [TTL=1800]` | принять показание влажности со сроком годности в секундах |
| `ACE_EXT_RH_ENABLE ACE=0 ENABLE=1 [RH_START=] [RH_END=] [TEMP=]` | включить автосушку для Pro в обход валидации |
| `ACE_EXT_RH_STATUS` | текущее значение, возраст, активен ли цикл, действующие пороги |

### Таймер

Период 60 с, совпадает с `AUTO_DRY_INTERVAL` в multiACE.

```
для каждого ACE с внешней влажностью:
    пороги ← ace._auto_dry_for(idx)       # настройки multiACE, не свои
    если не enabled                       → пропустить
    если показание протухло (age > ttl):
        если цикл наш и активен           → ace._auto_dry_stop(idx, 'rh stale')
        пропустить
    если печатает и not ace.auto_dry_while_printing → пропустить
    если цикл не наш, не идёт, rh >= rh_start → ace._auto_dry_start(idx, temp, why)
    если цикл наш и rh <= rh_end              → ace._auto_dry_stop(idx, why)
```

Единственное отличие от родного цикла multiACE — отсутствие проверки `_is_v2`
и другой источник числа. Запуск, остановка, разгон, сохранение состояния —
вызовы кода multiACE.

### Требования безопасности

1. **Протухшие данные гасят нагрев.** `_auto_dry_start` отправляет в ACE команду
   с `duration=600` минут: устройство само не остановится 10 часов, цикл гасит
   только тик. Поэтому при отсутствии свежих показаний дольше TTL активный цикл
   останавливается принудительно. Севшая батарейка датчика, упавший сервер или
   пропавший Wi-Fi не должны оставлять нагреватель включённым.
2. **Только свои циклы.** Цикл, запущенный пользователем вручную, модуль не
   останавливает никогда — та же семантика владения, что у multiACE.
3. **Пережитие перезапуска Klipper.** multiACE восстанавливает
   `_auto_dry_started` из `save_variables`. После перезапуска модуль не имеет
   свежих показаний, пока не придёт первое `ACE_SET_RH`; до этого момента
   активный цикл считается протухшим и гасится. Осознанный выбор: лучше лишний
   раз прервать сушку, чем греть вслепую.
4. **Значения вне диапазона отвергаются.** `RH` принимается только в 0..100,
   `TTL` в 60..7200. Мусорное число не должно приводить к нагреву.

## Компонент 2: `ace-rh-feeder` (сервер)

Размещение: `~/docker/ace-rh-feeder`, контейнер рядом с HA и mosquitto.

Курьер без собственной логики: раз в 5 минут читает датчик и передаёт значение.

```
цикл:
    rh, temp, battery ← чтение LYWSD03MMC по BLE
    POST http://<printer-ip>:7125/printer/gcode/script
         {"script": "ACE_SET_RH ACE=0 RH=<rh> TTL=1800"}
    публикация в MQTT для графиков в Home Assistant (необязательно)
    сон 5 минут
```

### Чтение датчика

Датчик: `AA:BB:CC:DD:EE:FF`, подтверждён живым чтением на сервере.
Характеристика `ebe0ccc1-7a0a-4b0c-8a1a-6ff2997da3a6`, уведомления, 5 байт:
температура `int16 LE / 100`, влажность `uint8`, напряжение батареи `uint16 LE` мВ.

Сток-прошивка вещает показания в зашифрованном виде (нужен bindkey из облака
Xiaomi), поэтому используется GATT-подключение — оно работает без облака и без
ключа. Проверено: 26.95 °C, 57 %RH, 3033 мВ.

Прошивка pvvx ATC_MiThermometer (открытый broadcast, экономнее по батарее,
слушать могут несколько потребителей одновременно) — возможное улучшение
позже. Интерфейс чтения в коде изолирован, чтобы замена не затронула остальное.

### Известная особенность адаптера

Realtek RTL8761BU на сервере имеет свойство залипать: LE-сканирование
перестаёт отдавать пакеты, при этом классическое обнаружение продолжает
работать, и внешне адаптер выглядит исправным. Лечится `power off` / `power on`
через BlueZ. Сервис обязан определять ситуацию (нет ни одного результата
сканирования) и перезапускать адаптер сам, иначе автосушка тихо ослепнет.

## Размещение датчика

Внутри камеры ACE Pro. Рабочий диапазон LYWSD03MMC — 0..60 °C, сушка идёт при
45..55 °C, то есть попадает в спецификацию, но без запаса. Температура датчика
передаётся вместе с влажностью и служит контролем: устойчивый выход за 60 °C —
повод понизить `auto_dry_temp`.

## Параметры по умолчанию

| Параметр | Значение | Источник |
|---|---|---|
| Порог старта | 45 %RH | `auto_dry_rh_start`, умолчание multiACE |
| Порог остановки | 35 %RH | `auto_dry_rh_end`, умолчание multiACE |
| Температура сушки | 50 °C | `auto_dry_temp`, потолок `max_dryer_temperature` = 55 |
| Мягкий старт | 50 °C, +5 °C каждые 5 мин | константы multiACE |
| Сушка во время печати | выключена | `auto_dry_while_printing` |
| Опрос датчика | 5 мин | сервис |
| Срок годности показания | 30 мин | `TTL` |
| Тик автосушки | 60 с | `AUTO_DRY_INTERVAL` |

Пороги меняются штатной командой multiACE и его веб-интерфейсом, без правки кода.

## Тестирование

Модуль на принтере тестируется с подставным объектом `ace` и управляемыми
часами, без реального нагрева:

- влажность выше порога, цикл не идёт → вызван `_auto_dry_start`
- влажность ниже порога остановки, цикл наш → вызван `_auto_dry_stop`
- цикл запущен вручную (не наш) → не трогаем ни при каких показаниях
- показание протухло, цикл наш активен → нагрев остановлен
- показание протухло, цикл не запускался → ничего не происходит
- идёт печать, `auto_dry_while_printing` выключен → цикл не стартует
- `RH` вне 0..100 → команда отвергнута, состояние не изменилось
- отсутствует ожидаемый приватный метод у `ace` → модуль отключается с ошибкой в логе

Сервис на сервере тестируется с подставным датчиком и подставным HTTP:

- корректное показание → отправлен верный G-code с верным значением
- датчик недоступен → `ACE_SET_RH` не отправляется вообще (не шлём старое число)
- Moonraker недоступен → повтор на следующем цикле, сервис не падает
- пустое сканирование → выполнен перезапуск адаптера

Живые проверки на железе выносятся отдельно и запускаются вручную.

## Что сознательно не делается

- Собственный конечный автомат сушки — он уже есть в multiACE и написан лучше.
- Собственное хранилище состояния — состояние ведёт multiACE.
- Правка `ace.py` — будет затёрта обновлением.
- Врезка в электронику ACE, ESP32, DHT11 — не нужны: беспроводной датчик
  покрывает задачу и имеет диапазон 0..99 %RH против 20..80 %RH у DHT11.
- Выбор профиля сушки по материалу из Spoolman — осмысленное развитие, но не
  в первой версии.
